# Мост поддержки · личные кабинеты

Реальное серверное приложение на Django 5.2 LTS: кабинет заявителя, отдельный доступ организации к явно назначенным задачам и рабочая очередь координатора в Django admin. Данные хранятся в PostgreSQL при развертывании. SQLite используется только для локальной разработки и изолированных тестов.

## Возможности первой версии

- Регистрация по приглашению или отключённая регистрация; вход по email и паролю.
- Обращение с номером, темой, статусом, следующим шагом и перепиской.
- Организация видит только отдельное описание назначенной ей задачи и отдельный диалог. Личная переписка заявителя, его email и исходное описание не передаются организации.
- Доступ требует проверенной организации, активного членства и зафиксированного согласия. Смена организации автоматически отключает доступ и очищает старые поля передачи до нового согласования.
- Координатор меняет статусы, назначает ответственных и отвечает через `/admin/` → «Сообщения». Внутренние заметки доступны только сотрудникам.
- Аудит событий, CSRF, экранирование пользовательского текста, HTTP-only cookies, защита от перебора и ограничения частоты запросов, общие для всех процессов приложения.

В этой версии нет загрузки документов, платежей, автоматической юридической консультации, подтверждения email, отправки уведомлений и самостоятельного восстановления пароля. SMTP-параметры подготовлены для последующего подключения; письма сейчас не отправляются, подтверждение email не имитируется.

## Кабинет организации

Веб-интерфейс в стиле приложения «Мост поддержки» доступен по `/partners/` после входа. Публичный просмотр `/partners/preview/` работает отдельно: демонстрационные записи сохраняются только в браузере, не читают API организаций и не отправляются в фонд. Кнопка примера помогает ознакомиться со сценариями без создания серверной учётной записи.

Основные разделы: обзор, заявки в фонд, проекты, сообщения по заявкам, услуги, документы-ссылки, организация и команда, отчёты CSV. Каталог документов хранит ссылки HTTPS; загрузка файлов в этой версии отсутствует. Отчёты отражают записи кабинета и не являются бухгалтерской или финансовой отчётностью.

Серверный режим требует проверенной организации и активного членства. Роли `manager`, `editor`, `viewer` разделяют управление карточкой, работу с записями и чтение. Изменение команды выполняется уполномоченным администратором; кнопка в кабинете создаёт запрос, а не выдаёт доступ самостоятельно. Название, тип и проверка организации не меняются через API рабочего пространства.

Заявки организации отделены от личных обращений мигрантов. Статусы и ответы фонда управляются через Django admin. Работодатели и кадровые агентства не получают доступ к направленным личным обращениям. Для остальных организаций действуют отдельное описание задачи, согласие и адресный доступ; приватное описание и личная переписка не выдаются.

Рабочее пространство сохраняется с номером ревизии. Одновременное изменение устаревшей версии возвращает 409: пользователь должен загрузить свежие данные. Все API проверяют членство при каждом запросе; публичный просмотр не предоставляет серверные права. Существующие режимы `closed` и `test` сохраняются при развёртывании.

## Режимы запуска

`REGISTRATION_MODE`: `closed` (по умолчанию), `invite` или `open`. Для `invite` нужен SHA-256 кода в `REGISTRATION_INVITE_SHA256`. Исходный код приглашения не хранится в репозитории.

`PORTAL_INTAKE_MODE`: `disabled` (по умолчанию), `test` или `live`. В тестовом режиме все экраны отмечены как тестовые, при создании обращения требуется подтверждение использования только вымышленных данных, а обращение помечается `is_test=True`. Для `live` обязательны согласованные `PORTAL_OPERATOR_NAME`, `PORTAL_POLICY_VERSION`, `PORTAL_POLICY_URL`. Наличие этих значений само по себе не заменяет проверку документов и готовности ответственных сотрудников.

Публичные кабинеты должны работать только по HTTPS. Для проверки через локальный SSH-туннель можно отключить `DJANGO_SECURE_SSL_REDIRECT` и `DJANGO_SECURE_COOKIES`; нельзя использовать такие настройки для публичного HTTP-входа.

## Разработка и тесты

Нужен Python 3.12 или другой поддерживаемый Django 5.2 Python версии 3.10+.

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py test --settings=config.test_settings
.venv/bin/python manage.py makemigrations --check --dry-run --settings=config.test_settings
```

Тестовые настройки используют отдельную базу в памяти и не подключаются к рабочей PostgreSQL. Тесты проверяют границы доступа между пользователями и организациями, отзыв доступа, передачу другой организации, защиту личной переписки, CSRF, XSS, приглашения, ограничение попыток входа и подмену служебных полей формы.

Секретный ключ и рабочие переменные задаются окружением. Образец — `.env.example`; приложение не загружает `.env` самостоятельно. Systemd должен использовать защищённый `EnvironmentFile`.

```sh
python manage.py migrate --noinput
python manage.py collectstatic --noinput
python manage.py check --deploy
python manage.py createsuperuser
```

Последняя команда интерактивно запрашивает первый пароль администратора. Не передавайте пароль аргументом команды и не сохраняйте его в репозитории.

Для сотрудника с ограниченными правами:

```sh
python manage.py bootstrap_coordinator --email coordinator@example.org --name 'Имя сотрудника'
```

Команда запрашивает пароль скрытым вводом. Она не изменяет существующие учётные записи. Доступ к управлению пользователями и организациями остаётся у администратора.

Раз в сутки запускайте `python manage.py prune_portal_data`: удаляются только истёкшие сессии и счётчики частоты запросов, обращения не удаляются.

## Развертывание

WSGI: `config.wsgi:application`; Gunicorn слушает только localhost. Nginx отдаёт статические файлы и перезаписывает `X-Real-IP`/`X-Forwarded-Proto`; `DJANGO_TRUST_PROXY=true` включается только с этим доверенным локальным прокси. PostgreSQL поддерживает переменные `POSTGRES_*` либо алиасы `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`; Unix-сокет задаётся в `DB_HOST`. Каталог статики задаётся `STATIC_ROOT`.

Проверка `/healthz/` возвращает только состояние соединения с БД. Приватные страницы не кэшируются и помечены `noindex`.

Подробные инструкции по сервисам, обновлению и резервным копиям находятся в `OPERATIONS.md`, когда инфраструктурная часть включена в поставку.
